# Go-to-Market Plan: <Launch Name>

## Positioning
The core value proposition and how it's differentiated.

- State what this is instead of, and for whom — positioning without a comparison point ("better," "faster") doesn't tell anyone why to choose it.
- Keep this to one clear statement teams can repeat consistently — if sales, marketing, and support would each describe it differently, positioning isn't done yet.

## Target audience
Who this launch is aimed at, and any segmentation.

- Link to the relevant persona(s) rather than redefining the audience here — segmentation should say which persona gets which message, not restate who they are.
- Note if this launch targets a narrower audience than the product's long-term audience (e.g. one segment first) — that shapes channel choice below.

## Messaging
Key messages per audience/channel.

- Tie each message back to a specific audience segment's problem, not a generic product benefit — the same feature can need different framing for different audiences.
- Keep messages consistent with Positioning above; if messaging drifts from positioning, pick one.

## Channels & timeline
| Channel | Owner | Date | Status |
|---|---|---|---|

- List every channel actually involved in this launch (email, in-app, blog, sales enablement, docs) — a channel left off this table is a channel nobody's accountable for.
- "Owner" should be a person, not a team — a launch item without a named owner tends to slip silently.
- Order or group rows by date so the table doubles as the launch runbook, not just a record.

## Success metrics
How launch success will be measured, and by when.

- Distinguish launch-activity metrics (signups, press mentions) from outcome metrics (retention, revenue) — both can matter, but they answer different questions.
- Set the "by when" explicitly — a launch metric with no deadline never definitively succeeds or fails.

## Cross-team dependencies
What marketing/sales/support need from product/engineering before launch, and by when.

- Name the specific asset or input needed (API docs, a demo environment, training materials), not just "engineering support."
- Flag dependencies with the earliest deadline first — a late dependency here is what most often slips a launch date.
